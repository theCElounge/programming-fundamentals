Lab Anomaly Detector

Use Python's exception handling to build a monitor that survives sensor failures and flags out-of-range readings without ever crashing.

Learning Objectives

By the end of this lab, you will be able to:

  1. Understand what an exception is and why programs raise them.
  2. Use try/except to handle errors without crashing the program.
  3. Distinguish between a sensor read failure and a valid-but-abnormal reading.
  4. Raise a custom exception when a reading is out of an expected range.
  5. Build a monitor that keeps running and reporting even when errors occur.

Part 1: What Is an Exception?

Back in Lab 3, you read temperature and humidity from the HS3003. Every program you've written since Lab 1 has assumed the sensor always answers correctly. In the real world, that's not guaranteed: a loose connection, electrical noise, or a momentary I2C bus conflict can cause a read to fail. When that happens, Python raises an exception — a signal that something went wrong, which stops the program immediately unless it's handled.

Python — Shell 
>>> 10 / 0
Traceback (most recent call last):
  File "", line 1, in 
ZeroDivisionError: division by zero

>>> int("not a number")
Traceback (most recent call last):
  File "", line 1, in 
ValueError: invalid literal for int() with base 10: 'not a number'

Without handling, an exception crashes the whole program — exactly what you don't want in a monitoring device that's supposed to run for hours or days unattended.

Part 2: try/except

A try/except block lets your program attempt something risky, and recover gracefully if it fails, instead of crashing.

Python — try_except_basics.py 
try:
    result = 10 / 0
    print("This line never runs")
except ZeroDivisionError:
    print("Caught it! Can't divide by zero.")

print("Program keeps running after the error.")
KeywordPurpose
try:Code that might raise an exception.
except ErrorType:Runs only if that specific error occurs inside the try block.
except Exception as e:Catches any exception; e holds the error's message.
finally:Runs no matter what — whether an error happened or not.

Applying this to a sensor read:

Python — safe_read.py 
import machine
from hs3003 import HS3003

i2c = machine.I2C(1)
sensor = HS3003(i2c)

try:
    temperature_c, humidity_percent = sensor.read()
    print(f"Reading OK: {temperature_c:.1f} C, {humidity_percent:.1f}%")
except OSError as e:
    print("Sensor read failed:", e)
💡 Why OSError? I2C communication failures in MicroPython are typically raised as OSError (the same exception type used for many hardware and file errors). Catching the specific type you expect is better practice than blindly catching everything.

Part 3: Read Failure vs. Abnormal Reading

There are two very different kinds of "wrong" a monitoring program needs to tell apart:

  • Read failure — the sensor didn't answer at all (a communication error). This is a Python exception.
  • Abnormal reading — the sensor answered successfully, but the number itself is outside a sane range (like 150°C in a normal room). This is a valid float that fails a business rule, not a Python error — unless we deliberately decide it should be.

Python lets you raise your own exceptions with the raise keyword, which is exactly how we turn "this number looks wrong" into something a try/except block can catch and handle consistently, right alongside real hardware failures.

Python — anomaly_check.py 
MIN_REASONABLE_TEMP_C = -10
MAX_REASONABLE_TEMP_C = 50
MIN_REASONABLE_HUMIDITY = 0
MAX_REASONABLE_HUMIDITY = 100

class SensorAnomalyError(Exception):
    """Raised when a sensor reading is outside a sane range."""
    pass

def check_reading(temperature_c, humidity_percent):
    if not (MIN_REASONABLE_TEMP_C <= temperature_c <= MAX_REASONABLE_TEMP_C):
        raise SensorAnomalyError(f"Temperature out of range: {temperature_c} C")
    if not (MIN_REASONABLE_HUMIDITY <= humidity_percent <= MAX_REASONABLE_HUMIDITY):
        raise SensorAnomalyError(f"Humidity out of range: {humidity_percent}%")
💡 Custom exception classes: class SensorAnomalyError(Exception): pass creates a brand-new exception type by inheriting from Python's built-in Exception. This is a preview of object-oriented programming — for now, all you need to know is that it behaves exactly like any other exception you can raise and except.

Part 4: Building the Anomaly Monitor

Now let's combine both kinds of error-handling into one long-running monitor that never crashes, logs every problem it encounters, and keeps a running count.

Python — anomaly_monitor.py 
import machine
import time
from hs3003 import HS3003

i2c = machine.I2C(1)
sensor = HS3003(i2c)

MIN_TEMP_C, MAX_TEMP_C = -10, 50
MIN_HUMIDITY, MAX_HUMIDITY = 0, 100

class SensorAnomalyError(Exception):
    pass

def check_reading(temperature_c, humidity_percent):
    if not (MIN_TEMP_C <= temperature_c <= MAX_TEMP_C):
        raise SensorAnomalyError(f"Temperature out of range: {temperature_c} C")
    if not (MIN_HUMIDITY <= humidity_percent <= MAX_HUMIDITY):
        raise SensorAnomalyError(f"Humidity out of range: {humidity_percent}%")

read_failures = 0
anomalies = 0
good_readings = 0

print("Anomaly monitor running. Ctrl+C to stop.")

while True:
    try:
        temperature_c, humidity_percent = sensor.read()
        check_reading(temperature_c, humidity_percent)

        good_readings += 1
        print(f"OK: {temperature_c:.1f} C, {humidity_percent:.1f}%")

    except OSError as e:
        read_failures += 1
        print(f"[SENSOR ERROR] Could not read sensor: {e}")

    except SensorAnomalyError as e:
        anomalies += 1
        print(f"[ANOMALY] {e}")

    except Exception as e:
        # Safety net: catch anything unexpected so the monitor never crashes
        print(f"[UNEXPECTED ERROR] {type(e).__name__}: {e}")

    finally:
        time.sleep(2)

    if (good_readings + read_failures + anomalies) % 10 == 0:
        print(f"--- Summary: {good_readings} OK, {anomalies} anomalies, {read_failures} failures ---")
💡 Order matters: Python checks except clauses top to bottom and uses the first one that matches. List more specific exception types (OSError, SensorAnomalyError) before a general Exception catch-all, or the specific ones will never be reached.

Appendix — Quick Reference

try/except/finally Syntax

Python 
try:
    risky_code()
except SpecificError as e:
    handle_it(e)
except Exception as e:
    handle_anything_else(e)
finally:
    always_runs()
